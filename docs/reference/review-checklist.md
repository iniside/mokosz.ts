# Review Checklist

The failure classes this project guards against. Implementers must not add an
instance of any class; reviewers pick the classes the touched files route to
and run each **attack**. A finding needs `file:line` and a concrete failing
scenario.

| Touched files | Classes |
| --- | --- |
| `src/api/` (Hono routes, request/response schemas) | 1, 2, 7 |
| `src/mastra/workflows/`, `src/mastra/agents/`, `src/mastra/index.ts` | 3, 4, 7 |
| `src/retrieval/`, `src/ingest/` | 5, 2 |
| `src/invoices/` (schema, validator, generator) | 6, 4 |
| `src/llm/`, `src/prompts/`, `profiles/*.yaml` | 4, 8 |
| `src/db/` (migrations, queries) | 2, 1 |
| `src/runs/` (run store, executor, events) | 1, 3, 7 |
| `tests/`, `src/evals/`, `evals/`, CI | 9, 10 |
| `web/` (React UI) | 11 |
| any | 0 |

## 0. Scope and second source of truth

Attack: list what the diff introduces and what that makes dead; find the dead
thing still in the tree. Find anything the plan step does not name, any
behaviour `SPEC.md` and the decisions do not ask for, and any v2 item from
`SPEC.md`.

## 1. Async correctness

Attack: a blocking call on the request or run path (`readFileSync`,
`execSync`, `spawnSync`, CPU-heavy PDF parsing on the event loop); a promise
that is never awaited, so its rejection escapes the `try` that should catch
it; a shared resource (`pg` pool, HTTP client) created per request instead of
once per process.

## 2. Data contract

Attack: a Zod schema that accepts what the spec forbids (no `.strict()` where
input is external, `.optional()` on a required field, `z.number()` for money
instead of a decimal string parsed with `src/decimal.ts`, decision 0013); a response that leaks
internal fields or differs from the API contract in `SPEC.md` §4; a migration that
disagrees with the queries or the pgvector dimension in config.

## 3. Workflow state and persistence

Attack: workflow state mutated in place instead of returned or set with
`setState`; a step output or state value the storage snapshot cannot
serialise (a `Decimal`, a class instance); a side effect before `suspend()`
that runs twice on resume; a resume payload not validated by the step's
`resumeSchema`; the wrong Memory `threadId`, so two conversations share
history; a run restarted on boot although interrupted runs must end `failed`.

## 4. LLM boundary

Attack: model output used without schema validation (no `structuredOutput`
schema, no Zod parse); a retry that hides a schema failure; a model built
outside the profile module; the model name hardcoded instead of read from the
profile; token or cost accounting skipped on an error path; temperature,
`num_ctx`, `think`, `keep_alive` or `top_k` not taken from the profile.

## 5. Retrieval and citations

Attack: a chunk that crosses paragraph boundaries or loses its `element_id`;
EN and PL chunks mixed in one result without a language filter; a bare
`element_id` used as a key instead of `{celex}#{element_id}`; an act or article
filter from the router silently dropped; a citation in the answer that is not
among the retrieved keys and still passes the verifier.

## 6. Deterministic validation

Attack: a rule done by the LLM that the spec makes deterministic (sums, VAT,
NIP checksum, dates); money arithmetic in JavaScript `number`; a defective
invoice that passes because a rule short-circuits on a missing field instead
of failing it.

## 7. Errors and observability

Attack: an exception swallowed or turned into a 2xx; a run that fails without
its status, cost and latency persisted; a trace span not closed on the error
path; secrets or full prompts with personal data written to logs.

## 8. Prompts and configuration

Attack: a prompt string inlined in code instead of `src/prompts/`; a profile
key read with a silent default that hides a typo (profile schema not
`.strict()`); an API key or env value read anywhere except the settings
module.

## 9. Proof soundness

Attack: revert the behaviour and see whether an assertion breaks; an expected
value copied from the current output; a mocked database or a hand-built
workflow state instead of the production path; a test that needs network or
an API key; a CI step that passes with zero tests collected.

## 10. Evals

Attack: an expected citation taken from the retriever's output instead of the
regulation text; an LLM judge without the reference answer or a fixed rubric;
p95 reported from a handful of runs without saying so; costs estimated instead
of taken from the recorded usage and the price table; results not stored with
the profile and the git sha.

## 11. UI

Attack: a screen that breaks on empty, loading or error data; a value
formatted differently from the API (cost, latency, dates); an approval action
without disabled state while it is in flight, so it can be sent twice;
screenshots not regenerated by `mokosz screenshots` after a visual change.
